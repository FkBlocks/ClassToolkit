# ClassToolkit 需求总纲与路线图

> 本文档汇总 ClassToolkit 重构期的全部需求、架构决策、工程量评估与版本路线。
> 所有需求均已在会话中讨论并确认技术可行性；标注"已拍板"的条目可直接照此开发，
> 标注"待拍板"的条目需在对应阶段动工前确认。

- **目标平台**：Windows 10 Build 1809+ / .NET 10 桌面运行时
- **目标设备**：教室触摸屏大屏一体机
- **状态**：规划完成

---

## 1. 项目定位与核心原则

ClassToolkit 是面向课堂的"**无焦点交互层**"：侧边栏、音量、PPT 助手、屏幕批注、
插件体系，全部是同一个技术底座上的窗口组件。

### 1.1 四条铁律（所有功能必须遵守）

| # | 铁律 | 说明 |
|---|---|---|
| 1 | **全程无焦点** | 任何功能不得激活窗口、不得抢夺键盘焦点、不得打断 PPT 全屏放映。课堂与互动必须无缝衔接 |
| 2 | **触摸优先** | 面向触摸大屏一体机，触控目标最小 48px，交互不依赖键盘/鼠标右键 |
| 3 | **兼容 Office 三版本 + WPS** | 演示控制类功能（PPT 助手、PPT 批注）必须同时支持 PowerPoint 2013/2016/2019 与 WPS |
| 4 | **墨迹不污染原文件** | 批注墨迹仅在放映会话内存中存活，放映结束全部丢弃，绝不写入 PPTX 文件 |

### 1.2 无焦点基础设施（所有新功能的公共底座）

在动工任何功能前，先建立三个共享模块（约 3 晚）：

```
NoActivateWindow    —— WS_EX_NOACTIVATE + WM_MOUSEACTIVATE→MA_NOACTIVATE 窗口基类
InputHookService    —— WH_MOUSE_LL（点击外部收起）+ 触摸坐标判断
WorkAreaService     —— 多显示器 / 任务栏 / DPI 换算工具
PresentationBridge —— Office/WPS COM 后期绑定封装（PPT 助手与批注共用，见 §5）
```

窗口不激活的代价是收不到键盘事件——本项目面向触摸屏，此代价可接受；
若未来需要键盘，走全局钩子（ZoomIt 等屏幕工具的同款路线）。

## 3. 需求一：左右对称侧边栏（废弃悬浮球）

**目标**：完全废弃现有悬浮球（`ClassToolkit/MainWindow.*` 全部重写），
改为左右两条对称的贴边侧边栏。

### 3.1 交互状态机

```
                    ┌─────────────────────────────────┐
     常态           │  工具模式（互斥：同一时刻只有一边展开）  │
  (左右两个把手) ─点击─▶  左把手点击→左菜单；右把手点击→右菜单   │
                    │  展开右边时，左边自动收起              │
                    └───────┬─────────────────────────┘
                            │ 点音量按钮 / 检测到媒体播放
                            ▼
                    ┌─────────────────────────────────┐
                    │  音量模式（互斥规则失效：两边同时弹出）   │
                    │  两边各一个竖滑条，数值实时同步          │
                    │  底部：返回工具按钮                    │
                    └───────┬─────────────────────────┘
                            │ 无媒体播放持续 5~8 秒 / 点外部 / 点返回
                            ▼
                          常态（收起）
```

### 3.2 具体需求点

| # | 需求 | 说明 |
|---|---|---|
| 1 | 收起态把手 | 半透明小矩形 + 朝屏幕内部的箭头；左侧箭头朝右 `›`，右侧朝左 `‹` |
| 2 | 上下自由移动 | 把手可沿屏幕边缘上下拖拽，X 坐标锁定在边缘，用 WorkArea 避让任务栏 |
| 3 | 点击展开 | 点击把手弹出竖向矩形菜单；菜单内容暂时保持现状（tools.json 列表 + 退出） |
| 4 | 互斥展开 | **已拍板**：同一时刻只有一边展开；展开右边时左边自动收起（实现简单 + 操作直觉） |
| 5 | 点击外部收起 | 保留现有 Popup 外部点击收起行为 |
| 6 | 翻页 | 菜单支持翻页（菜单项超过一页容量时）；v1 建议安卓式离散翻页 + 圆点指示器，吸附滚动待定 |
| 7 | 拖拽复用 | 复用现有 `GetCursorPos` + DPI 转换 + 边界钳制代码，仅改"X 锁边、Y 自由" |

### 3.3 技术要点

- 单进程双窗口：同一 `SidebarWindow` 类以 `Side.Left/Right` 参数创建两个实例；
- 互斥协调：`SidebarCoordinator`（约 40 行）持有两窗口引用，UI 线程内纯内存调用；
- `App.xaml` 由 `StartupUri` 改为代码手动创建两个窗口；
- Popup 菜单沿用现有实现与主题刷新机制（`RefreshMenuTheme`），零新增风险；
- 菜单数据模型提前升级为 `MenuEntry` 记录（`Id/Title/Action`），tools.json 只是数据源之一，
  为插件化预留插座（§7）。

| 决策 | 状态 |
|---|---|
| 左右各一条侧边栏（非"单条可停靠"） | ✅ 已拍板 |

## 4. 需求二：智能音量集成（废弃 VolumeRecovery）

**目标**：完全废弃 `ClassToolkit.VolumeRecovery` 项目（现为空壳），
音量控制集成进侧边栏；智能检测媒体播放并自动弹出音量条。

### 4.1 功能需求

| # | 需求 | 说明 |
|---|---|---|
| 1 | 智能检测 | 区分系统音频（提示音）与媒体音频（浏览器/播放器/PPT 等应用） |
| 2 | 自动弹出 | **已拍板**：检测到媒体音频时，左右两侧边栏**同时**弹出变为音量条，两滑条数值实时同步 |
| 3 | 手动调节 | 工具菜单内保留音量按钮，点击同样弹出音量模式 |
| 4 | 返回工具 | 音量条底部固定"返回工具"按钮，切回工具菜单 |
| 5 | 自动收回 | 音频结束播放后自动收回至待机态（含宽限期防抖） |
| 6 | 调节系统音量 | 调节 Windows 系统主音量（含静音支持） |

### 4.2 检测技术方案（Windows Core Audio + NAudio）

| 能力 | 接口 | 说明 |
|---|---|---|
| 区分系统音 vs 媒体音 | `IAudioSessionControl2.IsSystemSoundsSession()` | 系统已原生分类，一个方法调用直接判定 |
| 判断"真的在播放" | `IAudioMeterInformation.GetPeakValue()` | 会话"活跃"≠"在响"，峰值 > 阈值才算播放中 |
| 调节系统音量 | `IAudioEndpointVolume.SetMasterVolumeLevelScalar(0~1)` | 另有 `SetMute` 静音、音量变化事件回调 |
| 实现 | **NAudio（`NAudio.Core`，MIT 协议）** | 封装全部 COM 互操作，与 GPLv3 兼容 |

- 检测实现：500ms 轮询，枚举会话 → 排除系统音会话 → 存在"活跃 + 峰值超阈值"会话即判定播放；
- 防抖策略（待拍板默认值）：
  - 进入：连续 2 次轮询检测到播放（防误触发）；
  - 可选加强：连续播放 ≥ 2 秒才自动弹出（防 QQ/微信提示音闪出音量条）；
  - 退出：连续 5~8 秒无峰值才收回（歌曲间奏、暂停不算结束）。

### 4.3 关键技术难点（预披露）

| 难点 | 方案 | 预算 |
|---|---|---|
| **双 Popup 同时开，"点击外部收起"互相误杀** | 音量模式下两个 Popup 改 `StaysOpen=true`，挂 `WH_MOUSE_LL` 钩子手动判断坐标是否落在两个 Popup 矩形内，都不在则一起收 | 2~3 晚，全项目核心新增难点 |
| **无焦点弹出** | 沿用 `SWP_NOACTIVATE` 置顶 + Popup 挂 `WS_EX_NOACTIVATE` + `WM_MOUSEACTIVATE`→`MA_NOACTIVATE` | 1~2 晚 |
| 音量事件跨线程 | NAudio 回调在后台线程，回写 Slider 必须 `Dispatcher.Invoke`；双向同步加防反馈环标记 | 细节坑，务必注意 |
| 滑条同步 | 两 Slider 绑定同一 `VolumeService`；拖左 → 写系统音量 → 事件回推 → 两滑块同刷 | 模式成熟 |

### 4.4 新增配置项（设置页，约 1 晚）

| Key | 说明 | 默认值 |
|---|---|---|
| `AutoShowVolume` | 媒体播放时自动弹出音量条 | 开启 |
| `AutoHideDelay` | 播放结束后收回延迟（秒） | 5~8 |
| `MinPlayDuration` | 最短播放时长防抖（秒） | 2 |

### 4.5 废弃 VolumeRecovery 清理清单（约半小时）

| 动作 | 位置 |
|---|---|
| 从解决方案移除项目并删除文件夹 | `ClassToolkit.sln`、`ClassToolkit.VolumeRecovery/` |
| 移除"音量恢复"菜单项 | `data/tools.json`、`ClassToolkit.Core/Services/DataFileInitializer.cs` |
| 更新 README 功能描述 | 根目录 `README.md` |

## 5. 需求三：PPT 助手

**目标**：PPT 放映期间，在屏幕左下角和右下角显示左右翻页箭头，
箭头中间显示当前页数/总页数。全程无焦点。

### 5.1 功能与技术方案

| 能力 | 方案 |
|---|---|
| 翻页 | COM 自动化 `SlideShowWindow.View.Next()/Previous()`，不需要焦点 |
| 页码 | `View.Slide.SlideIndex` / `Presentation.Slides.Count` |
| 检测放映中 | `Application.SlideShowWindows.Count > 0` |
| UI | 又一个 NoActivate 窗口（左下/右下箭头 + 中间页码），复用 §1.2 底座 |

### 5.2 演示控制桥（PresentationBridge，PPT 助手与批注共用）

- **后期绑定**（`dynamic` + IDispatch）：编译期不引用 Office 主互操作程序集，
  运行时按实际安装版本自适应——Office 2013/2016/2019 的放映对象模型完全一致，一份代码通吃；
- **WPS 三层降级**（已拍板必须支持 WPS）：

| 层级 | 手段 | 兜底效果 |
|---|---|---|
| L1 | 探测 ProgID：`PowerPoint.Application` → 失败试 `KWPP.Application`，动态调用翻页/页码 | WPS 基本支持 |
| L2 | 轮询代替事件：不依赖 `SlideShowNextSlide`（WPS 事件支持最烂），每 300ms 读 `SlideIndex` | 页码刷新行为在 Office/WPS 上完全一致 |
| L3 | Win32 兜底：枚举顶层窗口找放映进程（`POWERPNT.EXE`/`wpp.exe`）+ `GetWindowRect` 定位；翻页由 PPT 助手箭头保证 | 即使 COM 全挂，批注蒙版与翻页仍可用 |

- ⚠️ WPS 怪癖必须真机实测：WPS 个人版免费，家里装一个即可验证；
  Office 三版本代码路径一致，测一个版本即代表三个。

## 6. 需求四：屏幕批注

**目标**：在普通环境（桌面/网页/PDF）与 PPT 放映环境下均可在屏幕上书写批注。
**这是全项目最难的单点（约 15 晚）。**

### 6.1 两种环境

| 环境 | 方案 | 难度 |
|---|---|---|
| 普通环境 | 全屏透明蒙版 + InkCanvas，无未知数 | ★★☆ |
| PPT 环境 | 见下，墨迹按页暂存 + 穿透切换 | ★★★★ |

### 6.2 PPT 批注（已拍板的墨迹模型）

- **墨迹仅在放映期间存活于内存**：`Dictionary<int页码, StrokeCollection>`，
  翻页时"存当前页 → 清画布 → 载入新页"；放映结束清空字典——**不保存、不导出、不写入 PPTX**；
- 识别 PPT 环境：`SlideShowWindows.Count > 0` + 监听放映开始/结束自动进出批注模式；
- 识别当前页：初始 `SlideIndex` + 轮询更新（见 §5.2 L2）。

### 6.3 保留墨迹的同时操作 PPT（笔/鼠标双模式）

| 模式 | 蒙版行为 | 结果 |
|---|---|---|
| 笔模式 | `WM_NCHITTEST` 返回自身 | 触摸被拦截 → InkCanvas 落墨迹 |
| 鼠标/操作模式 | `WM_NCHITTEST` 返回 `HTTRANSPARENT` | 触摸穿透给 PPT → 翻页、动画、超链接照常 |

- 关键点：穿透只影响触摸落点，不影响墨迹渲染——切到鼠标模式后已写墨迹仍然显示；
- PPT 动画流畅性天然成立：蒙版是独立分层窗口，PPT 在自己窗口渲染，互不阻塞；
- 多显示器：蒙版必须定位到**放映窗口所在屏幕**（`GetWindowRect(放映窗口)`），而非笔记本主屏；
- 掌心误触：v1 只响应第一触点、后续触点忽略（1~2 晚）。

### 6.4 已知限制（诚实披露）

1. 墨迹锚定**页码**而非 PPT 元素：页内元素动画移动时墨迹不跟随（外部程序无法获知元素位置），课堂场景够用；
2. 不承诺"保存批注"：v1 结束放映即丢弃；若未来需要导出，再评估方案。

## 7. 需求五：插件化

**目标**：第三方可开发插件并安装到项目本体，扩展设置选项、交互逻辑、主题样式、硬件支持等。
这是最终形态的收尾大工程（约 45~50 晚，分 v2.0 核心与 v2.1 安全增强两期，见 §10）。

### 7.1 技术路线（已评估）

- **同进程 + `AssemblyLoadContext`**：插件 DLL 与主程序同进程运行，UI 无缝嵌入，
  .NET 桌面插件事实标准（MEF 学习曲线高、进程外无法嵌 WPF UI，均不采用）；
- 新建 **`ClassToolkit.Plugin.Sdk`** 项目：只放接口，主程序与插件作者共同引用。

### 7.2 SDK 契约（草图）

```csharp
public interface IPlugin
{
    string Id { get; }        // 唯一标识，如 "com.example.camera"
    string Name { get; }
    string Version { get; }
    void Initialize(IPluginHost host);
}

public interface IPluginHost
{
    IConfigStore Config { get; }              // 每插件独立 config.json
    void RegisterMenuEntry(MenuEntry entry);  // 向侧边栏加菜单项
    void RegisterSettingsPage(string category, Func<FrameworkElement> factory);
    void RegisterTheme(IThemePalette palette);
    // 事件钩子：MenuOpening、ToolLaunching(可取消)、ThemeApplied、ExitRequested
}
```

- 安装形态：`Plugins/com.example.foo/` 一个文件夹 = 一个插件（`manifest.json` + 插件 DLL + 依赖）；
- 分发形态：`.ctplg` 安装包（见 §7.4）；
- 加载器放 `ClassToolkit.Core`（主程序与设置程序两个进程都要能加载）。

### 7.3 四个扩展诉求的落地方式

| 诉求 | 落地方式 | 难度 |
|---|---|---|
| 更丰富的设置选项 | 插件返回 UserControl，设置程序挂到分类页 | 中等 |
| 修改原有交互逻辑 | 事件钩子（如 `ToolLaunching` 可取消/替换）；v1 只暴露 3~5 个点，克制为上 | 最难 |
| 修改主题样式 | 插件返回调色板，合并进 ThemeService（优先级低于用户手选） | 简单 |
| 硬件支持（摄像头/麦克风） | 同进程插件即普通 .NET 代码，引 OpenCvSharp/NAudio 即可；宿主只需提供 UI 位 + 配置 + 生命周期 | 简单 |

### 7.4 分发与安装：.ctplg 包格式

- 自定义扩展名 `.ctplg`，本质是 ZIP（`System.IO.Compression`），单文件分发；
- 解包后仍是 DLL 代码——**格式是分发层，不是安全层**，真正的防线见 §7.7；
- 包结构：

```
xxx.ctplg（ZIP）
├── manifest.json     ← id / name / version / sdkVersion / entryDll / capabilities / sourceUrl / payload 哈希
├── payload/          ← 插件 DLL + 依赖 DLL + 资源
└── icon.png（可选）
```

- manifest 示例（节选）：

```jsonc
{
  "id": "com.example.camera",
  "version": "1.0.0",
  "entryDll": "Camera.Plugin.dll",
  "sdkVersion": "1.0",
  "capabilities": ["camera"]
}
```

### 7.5 安装流水线（五步）

```
① 解包     .ctplg → 临时目录
② 验哈希   校验 manifest 声明的 payload 哈希；并与市场索引中的审核哈希比对（防审核后调包）
③ 扫风险   Windows Defender CLI（MpCmdRun.exe）扫描临时目录 → 报毒直接拒绝安装
④ 提示     展示能力声明（"此插件将调用：摄像头、网络"）→ 用户确认（安卓式安装页）
⑤ 安装     原子移动到 Plugins/{id}/{version}/（同盘移动，中途断电不产生半成品）
```

- 顺序原则：机器检查全部在前，人工确认最后；
- 文件关联双击安装走 HKCU 注册表（无需管理员权限）；v1 可先只支持"拖入窗口 + 市场安装"；
- 装好的插件重启程序后生效（v1 不做热加载）。

### 7.6 发现与加载机制（PluginLoader）

**发现**：启动时扫描 `Plugins/` 每个子文件夹，读 `manifest.json` 登记成列表；
只读 JSON、不执行插件代码，单个插件损坏只跳过、不影响程序启动。

**加载**（每个插件独立隔离）：

```csharp
// ① 独立加载上下文（隔离 + 未来可卸载的钥匙）
var alc = new AssemblyLoadContext($"plugin:{manifest.Id}", isCollectible: true);

// ② 插件自己的依赖从自己的文件夹解析
alc.Resolving += (_, name) => {
    var depPath = Path.Combine(pluginFolder, name.Name + ".dll");
    return File.Exists(depPath) ? alc.LoadFromAssemblyPath(depPath) : null;
};

// ③ 按 manifest.entryDll 加载入口程序集
var asm = alc.LoadFromAssemblyPath(Path.Combine(pluginFolder, manifest.EntryDll));

// ④ 反射找 IPlugin 实现类
var pluginType = asm.GetTypes()
    .First(t => typeof(IPlugin).IsAssignableFrom(t) && !t.IsAbstract);

// ⑤ 实例化并注入宿主服务
var plugin = (IPlugin)Activator.CreateInstance(pluginType)!;
plugin.Initialize(host);
```

要点：

| 问题 | 答案 |
|---|---|
| SDK 接口怎么共用？ | `IPlugin`/`IPluginHost` 在 `ClassToolkit.Plugin.Sdk` 程序集，宿主与插件引用同一类型 |
| 插件之间会打架吗？ | 不会。独立 ALC，同名不同版本依赖互不干扰 |
| 插件崩溃会带崩主程序吗？ | 不会。每个插件 try/catch 包裹，失败跳过 + 记日志 |
| 同 id 装了两个版本？ | 按 semver 取最高版本，旧的忽略 |
| 两个进程各加载一次？ | 正常设计：主程序取菜单/钩子，设置程序取设置页 |

### 7.7 安全与信任模型（声明制 + 谎言检测 + 真引擎）

GPL v3 下，插件与主程序构成组合作品，**分发插件必须开源且 GPL 兼容**；
但"是否开源"是法律状态、技术扫描无法验证，只能由**市场政策 + 人工审核**执行。

四道防线：

| # | 防线 | 机制 | 作用 |
|---|---|---|---|
| 1 | 能力声明制 | 作者在 manifest 声明 `capabilities`；安装页知情同意 | 安卓式权限模型；"摄像头"等是中性能力，声明即合法 |
| 2 | 谎言检测 | Mono.Cecil 扫 IL，查**未声明的**敏感调用（网络/文件/P/Invoke 等） | 声明与实际不符才是风险信号，误报率低 |
| 3 | Defender 扫描 | `MpCmdRun.exe -Scan` 扫描 payload | 报毒直接拒绝；措辞"未发现已知威胁"而非"确认安全" |
| 4 | 市场人工审核 + 哈希绑定 | 审核源码；审核产物的哈希写入市场索引 | 杜绝"审核后调包"；GPL 开源要求在此落地 |

### 7.8 插件市场（轻量版）

- 形态：GitHub Pages 上的 JSON 索引（不是电商网站）；应用内"插件市场"页读取索引浏览/安装；
- 流程：作者提交 → 人工审核源码（GPL 开源要求生效）→ 通过后合并索引（含构建产物哈希）→ 用户应用内安装；
- 量级：生态初期一年约 10 个提交，单个审核约 20 分钟，个人完全可承担。

### 7.9 打包器（ctpack CLI）

- v1 做 CLI：`ctpack Foo.Plugin.csproj -o Foo.Plugin.ctplg`——收集构建输出 → 生成 manifest → 算哈希 → 打 ZIP（约 1~2 晚）；
- 必须保留**开发模式**：应用可直接加载未打包的插件文件夹，作者调试无需反复打包。
